Workflow

What happens, in order, from upload to finished export:

Amber dashed = optional, feeds into the main pipeline rather than sitting inline with it.

  1. Scene detection — PySceneDetect (Content or Adaptive, your choice) finds every cut in the source video, using the same sensitivity/minimum-length/detector settings as the "Scene Detection & Analysis" tool in Tools, so what you preview there is what actually gets used.
  2. Rating — each scene is rated on sharpness/brightness/duration/face presence (OpenCV), boosted by AI Vision's 1-5 quality rating, and boosted further for scenes with quotable dialogue when VISION + STT is selected (faster-whisper transcription).
  3. Beat/dialogue prep (optional) — if "sync cuts to beat" is on, a music track is prepared early and its beat grid drives cut timing; if dialogue transcription is on, word-level timestamps are generated for clean-cut alignment.
  4. Scene selection — highest-rated scenes are picked to fill the target duration, respecting min/max clip length and a minimum spacing between picks so the trailer isn't built from one over-represented stretch of the source, snapping cut points to the beat grid and/or word boundaries when enabled, and topping up across a few passes to land within ~0.5s of the target length.
  5. Assembly — selected scenes plus title/end cards are concatenated with the genre's signature transition (see table below), or a custom transition driven by an uploaded matte video/image if selected; any clip that fails to extract is dropped and the reported scene count reflects what actually made it in.
  6. Audio level normalization — SOT is loudness-normalized immediately after assembly so every later step works off a predictable baseline.
  7. SFX at cuts — Woosh (Sony AI) generates the hit sound from the genre's SFX prompt; if Woosh isn't reachable, "From genre" is disabled rather than falling back to another model, since ACE-Step is a music model, not an SFX model. A procedural synth fallback still applies if Woosh returns an unusable result mid-job.
  8. Background music — ACE-Step-generated or uploaded, normalized, and ducked under SOT.
  9. Narration (optional) — Fish Audio S2 (self-hosted or cloud) generates speech from a script using a voice picked from that engine's live voice list or an uploaded reference sample cloned zero-shot, or an uploaded VO track is used instead; either way it's loudness-normalized before mixing.
  10. Final audio mix — if a voiceover is present, SOT ducks to near-silence under it via a live sidechain; BGM ducking works differently — dialogue/SOT gaps are silence-detected up front, any gap shorter than your configured hold is bridged so a brief pause doesn't let the music swell back up and immediately duck again, and the resulting windows drive a deterministic volume dip (not a reactive compressor) applied to BGM only during genuine talking stretches. If "broadcast dual-mono" is on, the result is collapsed so every element is identically audible in both channels; a final loudness/true-peak pass targets your configured broadcast spec.
  11. Export — download as MP4 (H.264 High Profile), Apple ProRes 422 HQ (29.97 or 23.976fps), or an AVC-Intra 100i approximation.

Jobs run through a concurrency-limited queue (default 2 at a time, configurable via /api/queue/limit) so multiple simultaneous requests don't overload the local model servers (ACE-Step, Woosh, Ollama, Fish Audio). Two jobs from different people can run at the same time; a third waits in line and shows its position.

Job monitor & saved trailers

Two collapsible panels sit above the generator form:

  • Job monitor — a live, whole-server view of what's active (currently processing, with a progress bar), queued (waiting for a free concurrency slot), and recently finished (last hour, tagged Done/Error/Cancelled).   • Saved trailers — every trailer that's finished successfully is kept permanently (SQLite-backed, survives a server restart) until someone deletes it. Neither panel is per-user — there's no login system, so everyone hitting this server sees the same jobs and the same saved trailers.

Player format compatibility

The Player streams files directly from the browser — nothing is re-encoded on the server for a file the browser can already decode. Broadcast masters are routinely something a browser can't decode natively (ProRes or DNxHD in a .mov, most MXF), which shows up as a blank frame or a media error with the controls still present.

When that happens the Player converts automatically: the moment its <video> element reports an error, it calls POST /api/media/playable with the staged filename, which re-encodes to H.264/AAC MP4 (audio kept) and hands back a URL that plays. The converted copy is cached under UPLOAD_FOLDER, so picking the same file again is instant. This only applies to files picked via Browse library — a file chosen from your own machine plays straight from a local blob URL with nothing uploaded, so there's nothing on the server to convert if your browser can't decode it locally.

Text to SFX

Generates a one-shot sound effect from a free-text description via Woosh, Sony AI's sound-effects model — separate from the genre-based SFX the promo generator stamps at scene cuts automatically. Describe the sound concretely ("glass shattering", "footsteps on gravel") rather than a mood — Woosh is a sound-effects model, not a music model, so style adjectives do less work here than in the Music tool.

The actual request schema, confirmed against Woosh's own api_server.py: the server expects {prompt, token} and responds with FLAC, not WAV — token is a required field the server never actually validates, so "string" (the same placeholder Sony's own test script sends) satisfies it with nothing for you to configure. duration is not a real field on this API's GenerateArgs at all; requesting a specific length is enforced afterward by trimming the response locally with ffmpeg, since the API has no way to ask Woosh for one directly. Samples works the same way as before: the same request sent multiple times in a row, each trimmed independently, rather than an invented batch parameter.

Like the Music tool, this has no fallback: if Woosh is unreachable it says so rather than substituting a placeholder sound. The trailer pipeline's own SFX-at-cuts step is different — it falls back to a procedural synth click when Woosh is down, because that stage always needs something to stamp at each cut; a tool you're explicitly invoking to generate a specific sound should tell you it failed instead.

POST /api/sfx/generate  + prompt, duration, samples

AI Chat

A plain chat interface over whatever models Ollama has installed — separate from the vision/rating pipeline the promo generator uses, and nothing typed here feeds into a job. Useful for testing how a model behaves, drafting text, or just asking it something directly.

The conversation lives only in the page — there is no server-side session and nothing is saved, so switching tabs or reloading starts fresh. Every send resends the full conversation so far (Ollama has no server-side memory of its own between calls), capped at CHAT_MAX_HISTORY messages (default 60) to bound the request size on a very long conversation.

Show model reasoning requests Ollama's think mode for models that support it, and renders the reasoning in a collapsed "Reasoning" block under the reply rather than mixing it into the answer. Off by default, since most models don't need it and it roughly doubles response time.

Responses are not streamed — the full reply comes back in one request. This keeps the implementation simple and consistent with the rest of the app (job progress here is polled, not pushed, for the same reason), at the cost of watching a "Thinking…" status instead of text appearing as it's generated.

Assistant replies are rendered as markdown — headers, bold/italic, inline code, fenced code blocks, and lists all display properly rather than showing raw **/#/- characters, which is what some models return unprompted for anything resembling a structured answer. This is a small built-in renderer, not an external library — the app has no CDN dependencies, matching a LAN deployment with no assumed internet access — and everything it emits as HTML is built from text that was escaped first, so a reply containing something that looks like a tag or script can't affect the page. Your own typed messages are never run through this — they show exactly as typed, so a literal asterisk you type stays a literal asterisk.

Attachments

Images — attach via the paperclip button, or paste directly from the clipboard (e.g. a screenshot). Handled entirely in the browser: read, base64-encoded, and sent straight through in Ollama's own messages[].images field with no server round trip. Only useful with a vision-capable model — a text-only model will typically just ignore them. Capped at CHAT_MAX_IMAGES_PER_MESSAGE (default 4) and CHAT_MAX_IMAGE_BYTES (default 8MB) per image, checked in the browser and re-checked server-side.

Documents (PDF, plain text, common code/markup files) — a PDF can't be parsed reliably in the browser, so these go to the server for text extraction first; the extracted text is folded into the message sent to the model, wrapped in --- attached: name --- markers, but is kept out of the visible chat bubble (which shows a filename chip instead) so a long document doesn't fill the conversation with a wall of text. Capped at CHAT_ATTACH_MAX_BYTES (default 8MB) per file and CHAT_ATTACH_MAX_CHARS (default 20,000) of extracted text; longer documents are truncated and flagged as such to the model.

PDF extraction needs the optional pypdf package on the server (pip install pypdf --break-system-packages); without it, PDF attachments fail with a clear message while plain text and code files continue to work. A scanned/image-only PDF with no real text layer also fails clearly rather than silently attaching nothing.

Both attachment types stay in the conversation history for the rest of the session (the same way the text does), so a long conversation with several images or documents attached can grow the request size substantially — there is no attachment-specific pruning beyond the existing CHAT_MAX_HISTORY message cap.

Theme

The three buttons under the app name in the rail — ☀ / ☾ / ⚙ — switch between light, dark, and Auto, which follows your OS or browser's light/dark setting and updates live if that changes while the page is open (e.g. a system that switches at sunset). Auto is the default until you pick one explicitly.

The choice is stored in your browser's own local storage (aimp_theme), not on the server — it's per-browser, not shared across devices or people. The theme is resolved and applied before the page's stylesheet is even parsed, so there's no flash of the wrong theme on load, and if local storage is unavailable (private browsing, a locked-down browser policy) it falls back to dark, matching the app's original default.

Access control

Every route — the UI, uploads, library files, template assets, all API endpoints — requires a signed-in session. What exists:

  • Per-user accounts, stored (username + salted/hashed password + role) in users.db next to the trailer library. Roles are admin or user; admins get a Manage users link in the rail (/admin/users) to create accounts, change roles, disable/enable, reset passwords, or delete accounts. Regular users can use the app but can't reach /admin/users.
  • First-run bootstrap — if users.db has no accounts yet (a fresh deploy), a default admin is created automatically: username admin, password Aimp#Admin2026! (hardcoded as DEFAULT_ADMIN_PASSWORD near the top of this file — not a secret, since it's in source). Override with ADMIN_USERNAME/ADMIN_PASSWORD env vars, and change this account's password from Admin > Users right after first login.
  • Lost the admin password? Set RESET_ADMIN=1 (optionally with ADMIN_USERNAME/ADMIN_PASSWORD) and restart — this resets that account to an active admin with a new password every boot (falling back to the same hardcoded default if ADMIN_PASSWORD isn't set), regardless of what's already in users.db, and creates it if it doesn't exist. Remove RESET_ADMIN afterward, or the account keeps getting reset to that password on every restart.
  • Rate limiting on the direct file routes (/uploads/, /library/<id>/*, /download/, template /asset/), always on — FILE_ROUTE_RATE_LIMIT requests per IP per minute (default 40). This exists because those routes are otherwise reachable by anyone who can reach the port: library IDs are sequential and upload filenames are guessable, so without a limit a script could enumerate every trailer ever generated.
  • Rate limiting on login attempts — LOGIN_RATE_LIMIT tries per IP per 5 minutes (default 8), so a password can't be brute-forced at line speed.

The session cookie is signed with a key in SECRET_KEY_FILE (a .secret_key file next to this script by default), generated once and reused — regenerating it on every restart would silently log everyone out on each pm2 restart. Keep that file, and users.db, out of version control.

Sessions last SESSION_LIFETIME_DAYS (default 30). The cookie is marked Secure only when FORCE_HTTPS=1 is set — on the plain-HTTP LAN deployment this app defaults to, a Secure cookie would never actually be sent, which would look like the gate silently not working.

There's no audit trail beyond each account's last login timestamp shown on the Manage users page — actions inside the app (renders, deletes, template edits) aren't currently attributed to a specific user.

Templates

A template is the complete configuration for a programme: its rating mode and target duration, genre, transition and crossfade, scene-detection thresholds, loudness and ducking targets, narration engine/voice/language — plus its background music bed, SFX one-shot, voiceover, title card and end card (each card with an optional card VO and in/out points).

Genre is one of the fields a template carries, not an alternative to it. Picking a template at the top of the form fills everything in below, including the genre; you can then change anything you like and it applies to that job only, leaving the saved template untouched.

Templates are stored in TEMPLATES_DIR (a show_templates/ folder next to this script by default, overridable with that environment variable), with metadata in a small SQLite database, so they survive server restarts. Each job gets its own copy of a template's files, so nothing the pipeline does to them can damage the saved originals.

Building a template

Set the form up the way that programme should be made, pick whichever files belong to it in the ordinary Background music / Sound effects / Narration / Title card / End card sections, type a name in Save as template at the bottom of the form, and click the button. Local uploads and files picked with Browse library both work. The source video in the dropzone is never uploaded by this button — only the assets.

Saving under a name that already exists updates that template: the settings are replaced, and only the asset slots you supplied this time are rewritten, so you can swap just the music bed without touching the cards. Replacing a slot deletes the old stored copy, so the folder does not accumulate orphans. A template can also be pure configuration with no assets at all.

Using a template

Pick one from the Template dropdown at the top of the form. The summary box shows its rating mode, duration, genre, transition and which asset slots it fills; the form below is populated to match. The music/SFX/narration mode selectors switch to "Upload" for the slots it supplies, and the VO placement and card in/out numbers prefill, so nothing is applied invisibly.

A template is a set of defaults, not a lock. Anything you set explicitly wins for that job: attach a one-off music bed and it is used instead of the template's; set Background music to None and the job runs without music even though the template has a bed. Slots a template leaves empty behave exactly as they would with no template selected.

Deleting a template removes its row and its stored copies of those files. Trailers already generated from it are unaffected — they are finished renders in the trailer library, with no link back.

Getting ACE-Step to actually sing your lyrics

Skipped words, lines sung out of order, and an unexpectedly long instrumental intro before the vocal starts are widely reported ACE-Step behaviors, not a sign the app is misconfigured — see the model's own issue tracker ("Dont follow lyrics!") for the same complaint from other users. Two things this app already does to reduce it, and a few you control per-generation:

  • Thinking mode is always disabled for both music calls (thinking: false) — one of the most commonly reported triggers for the model wandering into an unrequested instrument or skipping straight to the chorus is specifically "Think mode," per the issue above.
  • The vocal-suppressing negative prompt is dropped whenever you supply lyrics — leaving it in alongside real lyrics is a separate, documented cause of confused, half-sung output (the model tries to satisfy "no vocals" and your lyrics at once).
  • Match lyric length to duration. ACE-Step sings at roughly 2–3 words per second. A 30-second track wants on the order of 60–90 words — noticeably more and it crams or drops lines to fit; noticeably less and the remaining time becomes instrumental filler, which is the usual cause of "too much intro." The Music Generation tool checks this live as you type and flags it before you generate.
  • Keep lines short — 4–8 words per line. Longer lines are reported to fracture vocal timing, since the model has to cram more syllables into the same beat than it can comfortably fit.
  • Use [verse] / [chorus] / [bridge] structure tags spanning the whole lyric. Without them the model decides the song's structure itself, which is the other common source of a long unrequested intro — explicit tags give it a map to fill the requested duration with, rather than improvising one.
  • Very long durations with long lyrics compound the problem — more lyric text competes with music generation for the same fixed model context, so a long song with dense lyrics is more likely to cut off before the end than a short one. If a long track keeps losing its last few lines, shortening the lyrics tends to fix it faster than raising the duration further.

None of this guarantees a perfect line-for-line reading — even well-paced, well-structured lyrics can come out with an occasional skipped or substituted word. If the track otherwise has the right energy, that's usually not worth regenerating over.

Narration delivery tags (Fish Audio)

Fish Audio reads inline markers out of the narration text itself to control emotion, delivery and non-speech sounds. There is no separate field — a tag is simply part of the script, and it is not spoken.

The syntax depends on the model generation: S2 uses square brackets ([happy]) and also accepts free-form descriptions like [very excited] or [warm and reassuring]; the older S1 uses parentheses ((happy)) with a fixed tag set. The app picks the right one automatically from FISH_AUDIO_MODEL — override it with FISH_TAG_STYLE=s1 or s2 if your self-hosted checkpoint does not match its name.

A tag bar sits under the script box in both the Narration section of the generate form and the Fish Audio S2 tool. Click a tag to insert it at the cursor; spacing around it is handled for you.

[confident] Tonight, the story everyone is talking about.
This is [emphasis] the one you cannot miss.
[whispering] Some secrets do not stay buried. [break] Only on GMA.

Placement matters: an emotion cue works best at the start of the sentence it applies to, while delivery cues like [emphasis] go immediately before the word they should stress. Sound and pause markers can go anywhere.

Two tags can be stacked for a combined effect — [sad][whispering], [angry][shouting] — but three or more in one sentence tends to produce worse results, not better. Keep to one emotion per sentence and space changes out; piling tags into a short promo line is the most common cause of a flat or erratic read.

The bar shows a curated set that suits promo scripts rather than the full catalogue. Since S2 accepts natural language, anything not listed can simply be typed in brackets.
